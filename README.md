# Telegram UserBot

Многофункциональный юзербот на Telethon с RP-командами, загрузкой медиа (YouTube / Instagram / TikTok), стелс-функциями и AI-помощником (Gemini + OpenRouter).

## Запуск

```bash
pip install -r requirements.txt
python main.py
```

### AI-помощник

Ключи необязательны: без них AI-команды отвечают понятной ошибкой, остальной бот работает как раньше. Пока не задан хотя бы один ключ, бот **не копит** историю личных сообщений; после настройки контекст начинается с новых сообщений, а прошлое можно догрузить через `!sync`. Картинки понимает только Gemini, поэтому `!ocr` требует `GEMINI_API_KEY`.

#### Слежка за сообщениями в ЛС
| Команда | Описание |
|---------|----------|
| `!pmwatch` | Показать, в каких ЛС слежка за удалениями/правками выключена |
| `!pmwatch mute @user\|ID` | Не следить в этом ЛС: кэш сообщений и сохранённые медиа чистятся |
| `!pmwatch unmute @user\|ID\|all` | Вернуть чат (или все) в мониторинг |

Слежка за удалениями/правками ЛС по умолчанию идёт **во всех** ЛС; `!pmwatch mute`
выключает конкретный чат полностью — его сообщения не кэшируются, медиа не
скачиваются, уведомления не отправляются. Выключение чата сразу чистит уже
накопленный кэш. Переписка в других ЛС продолжает отслеживаться.

Каналы детекции (максимальная точность): событие `UpdateUserStatus` (мгновенно), опрос статуса с адаптивным интервалом (база **1 с** до 5 целей, 5 с до 15, дальше 8–12 с; порог меняется `ONWATCH_MIN_INTERVAL`), typing-апдейты, входящие сообщения и галочки. Все созревшие цели опрашиваются **одним** GetUsers-запросом (по 150, через `get_entity(list)` — в Telethon 1.44 `get_users` удалён), а не N отдельными вызовами — поэтому короткий шаг не упирается в FloodWait; активность цели (typing/сообщение/галочки/правка) дополнительно ставит её в ближайший батч вне расписания. Плюс бесплатные «боковые» сигналы активности: смена имени/username, новая сторис, реакция на ваше сообщение, входящий звонок (самый сильный — человек был в сети секунду назад) и правка своего сообщения в ЛС. Всё, кроме смены профиля, учитывается только в ЛС с вами. Если трек перестаёт опрашиваться (аккаунт удалён или его нет в кеше сессии), владельцу один раз приходит уведомление во внешнем боте, а `!onwatchstatus` показывает причину и сколько она висит.

Источники в истории (`!onwatchlog`, колонка `source`): `status` (реальный вход по
статусу), `flicker` (пропущенная сессия по `was_online`), `poll`/`update` (поллер и
событие), `typing`, `message`, `read`,
`update-profile`, `update-story`, `update-reaction`, `update-call`, `update-edit`.
Отдельно, только строкой истории без уведомления: `reaction-group` (реакция в общем
чате) и `story-channel` (сторис канала, где цель — автор). При добавлении нового
канала источник нужно внести в `_ACTIVITY_LOG_SOURCES`, иначе он не попадёт в историю.

Тон уведомления во внешний бот различается по каналу: 📞 звонок, 📸 сторис,
📝 профиль, ✏️ правка, 💬 typing, 👍 реакция, 👁 прочитано; обычный вход —
нейтральное «появился в сети». Каждая пара «эмодзи + подпись»
уникальна (закреплено тестом).

**Строгий режим:** уведомление только при входе в сеть — даже если человек вышел всего на 2 секунды и вернулся. Уход из сети (`offline`, `«недавно» → «не в сети»`, свежий `was_online`) **не уведомляет**: он только пишется в историю и рвёт сессию. Любое наблюдённое состояние «не в сети» разрывает сессию и пишет `last_exit` (в `!onwatchstatus` — «Последний выход»). Следующий вход считается новой сессией: вместо обычного `_FIRE_COOLDOWN` (3 с) действует `ONWATCH_REENTRY_MIN_GAP` (1 с), поэтому 2-секундный возврат не глушится. Пока выхода не было, повторы внутри сессии (typing/сообщения/галочки/смена статуса) подавлены кулдауном и флагом активности с таймаутом 15 минут тишины. История сессий хранится 90 дней и чистится периодической задачей поллера.

Мгновенность: `UpdateUserStatus` обрабатывается сразу. `connection_watcher`
опрашивает `client.is_connected()` раз в секунду и после реконнекта запрашивает
внеплановый батч-опрос, не дожидаясь шага поллера. Таймаут установки
соединения у клиента снижен до 5 с (`timeout=5`), чтобы восстановление
начиналось быстрее. Это скорость реакции на уже зафиксированный разрыв, а не
скорость его обнаружения: мёртвый link Telethon замечает по своим внутренним
таймаутам, поэтому фактическая задержка = внутренний таймаут клиента + до 1 с. `catch_up` у клиента намеренно выключен:
накопленные за оффлайн апдейты пришли бы с опозданием и переписали бы статус
задним числом, а пропущенную сессию караул определяет по `was_online` (flicker)
с реальным временем выхода.

Эксплуатация: сторож соединения не умирает от ошибок (лог и повтор через 5 с),
флаппинг связи дебаунсится (не чаще одного батч-опроса за 20 с), неудачный
прогрев повторяется с паузой 15 с, после трёх неудач — обычный батч-опрос по
расписанию, и через 5 минут прогрев пробуется снова: деградация временная. Сброс
расписания помечается поколением — если реконнект случился во время прогрева,
устаревшие сроки не записываются, и цикл начинается заново.

Что покрыто только живой сессией (юнит-тесты сюда не достают):
- разрыв и восстановление реального MTProto-link, включая внутренние таймауты Telethon;
- фактическая доставка сервером `UpdateReadHistoryOutbox` (галочки в ЛС);
- реальные значения `was_online` у целей с видимым last-seen (flicker-окно на настоящих данных).

Остальное — статус-апдейты, typing, in-ЛС сообщения, галочки, flicker и
сессионная модель — проверяется wire-тестами: объекты сериализуются и
разбираются обратно через `BinaryReader`/`from_reader`, а события собираются
штатными builders Telethon (`UserUpdate.build`, `MessageRead.build`).

Ограничение слоя Telethon 1.44: `UpdateUserPhoto` (смена аватара) и `UpdateStoryViews` (кто посмотрел вашу сторис) в этой версии не доставляются отдельными апдейтами — каналы появятся вместе с библиотекой.

Пропущенные сессии (flicker по `was_online`) требуют Telethon ≥ 1.37.

### RP-команды

Работают **только в личных сообщениях**. Для отправки RP-действия:

- **Любой пользователь** в ЛС — пишет команду, бот отвечает
- **Owner/Sudo** — реплай на чьё-то сообщение с командой (RP от имени бота к этому человеку)

Более 90 RP-действий. Список: `!rphelp`

## Зависимости

- `telethon` — работа с Telegram API
- `yt-dlp` — загрузка YouTube / TikTok / Instagram (видео, аудио, карточки)
- `edge-tts` — озвучка `!tts` (Gemini/OpenRouter вызываются по HTTP, без SDK)
- `curl_cffi` — обязателен для TikTok/Instagram (имперсонация браузера в yt-dlp)
- `requests` / `aiohttp` — HTTP-запросы
- `flask` — веб-статус

## Статистика и тесты

- `GET /stats` — JSON-дашборд (команды, треки onwatch, напоминания, размер media/).
- Тесты: `python -m unittest discover -s tests -v`. Тесты не требуют `.env`
  (значения-заглушки задаёт `tests/test_downloaders.py`, а CI задаёт их через env).
- Ответы AI приходят в Telegram HTML: `!vibe`, `!liar` и `!summary` запрашивают
  строгий JSON (режим JSON у Gemini/OpenRouter) и рендерятся детерминированно,
  остальные AI-команды конвертируют Markdown модели в безопасный HTML. Сырые
  `**`, `>` и `*   ` в чат не попадают.
- `!vibe` показывает шкалы с визуальным баром, цитаты-доказательства, динамику,
  триггеры и совет. `!liar` — вердикт, шкалу достоверности, цитаты с датами,
  контекстом и уровнем серьёзности, неподтверждённые утверждения и вопросы.
  Обе команды считают количество проанализированных сообщений локально.
